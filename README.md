# Joker Chess

Chess plus one **Joker Move** per player per game: a queen, rook, bishop or knight teleports to any empty square. No capture, no check on the opponent's king afterwards, own king must be safe (so it can block a slider check). Kings and pawns can't use it. Everything else is standard chess; a rook that teleports loses its castling right.

Play: https://golden-chess.com (bot, two players on one device, online rated games, invite a friend by link).

The site has five tabs, like a chess site: **Play** (time control, Play, Play a friend by link or on one device), **Bots** (eight characters, one per engine level, from Pip at 600 to Golden at 2500), **Learn** (what the Joker Move is, autoplay boards, three one-move puzzles), **Ratings** (leaderboard per pool) and **Profile** (name, ratings, the latest games, settings). A bottom tab bar on phones, a side rail on wider screens; the address hash names the tab (`#play`, `#bots`, `#learn`, `#ratings`, `#profile`, `#games`, `#signin`, `#game`), so the browser's back button works. Each screen has one main action in gold and at most one quieter one. Nothing needs an account: Play starts a rated online game at once as a guest (an anonymous account with a made-up name); signing in (the chip on the start screen, Profile, the result card) keeps that progress on any device. Bot games have no clock, and the bot takes a human-like pause before each move (shorter in the opening, on forced moves and recaptures, longer in rich positions and before its Joker Move).

## Online play

- Clients only read the database; every change goes through the `play` edge function, which replays the game with the same rules module, checks the move, runs the clocks on server time (150 ms lag credit per move) and settles results and ratings.
- Writes are guarded by a row `version`, so two simultaneous requests can never both apply.
- Each state change is broadcast on a private Realtime channel `g:<game id>`; clients also poll as a fallback. Own moves are shown at once and confirmed by the server; a rejected move rolls back.
- A flag falls on the server: the client that sees a clock at zero asks the server to settle it (`claim`). A player who doesn't make a first move within 30 s gets the game aborted.
- Matchmaking pairs the closest rating with the same time control and rated/casual choice. Invites are links (`?join=<id>`); a third person opening one watches.
- Accounts: a visitor starts as a guest (Supabase anonymous sign-in). Online play (Play, Play a friend, an invite link) asks a guest for nothing: `requireAccount` only makes sure the session is there and goes on (Nov 2026; before, it sent guests to the sign-in page first). The sign-in page is reached from the start screen's chip, Profile and the result card's "Save progress"; an action started from there is remembered (`goldenchess.pending`, 30 min, also across a reload or the email link) and continues right after. Signing in adds an email to that same account (`updateUser({ email })` + a 6-digit code, `verifyOtp` type `email_change`), so anything the guest had stays, an email that already has an account signs in to it (`signInWithOtp` + code, type `email`). After any sign-in a player without a name of their own is asked for one (`profiles.name_chosen`, set by a trigger when the `rename` action saves a name; the name on the Google account is offered); Profile → Change name opens the same form. The email also carries a one-tap link for the same device. The server marks a profile registered (`profiles.is_guest = false`) from the token's `is_anonymous` claim. Sign out leaves a fresh guest. Email templates and the Auth settings they need: `supabase/emails/README.md`. Google never talks to Supabase's address, so its pages name golden-chess.com: on the website Google's own button (Google Identity Services, client `googleClientId` in `build.js`); in the app (Google refuses sign-in inside a web view) and on the website without Google's script, Google's sign-in page (`response_type=id_token`) answers to `google.html`, which hands the ID token back (the app: through the system browser and `goldenchess://auth`; state and nonce are checked against `goldenchess.gFlow`). The ID token is linked to the guest (`linkIdentity({ token, nonce })`) or, when that Google account or its email already has a player, signs in to that player (`signInWithIdToken`, then the page starts over as them). The Google client needs only golden-chess.com: JavaScript origin `https://golden-chess.com`, redirect URI `https://golden-chess.com/google.html`. The iPhone app (from build 1.1) offers Sign in with Apple natively (`appleShown()`, the plugin in `app/plugins/apple-sign-in/`; the ID token goes to the same `signInWithIdToken` / `linkIdentity` path, Supabase's Apple provider with the bundle id as client id) and Google beside it; the 1.0 build, without the plugin, has the email code alone (the App Store asks for Sign in with Apple next to any other company's sign-in, guideline 4.8), and the same email reaches the same account.
- House players (`profiles.house`, table `house`, 223 of them, seeded by the migrations `20261106140000_house_seed.sql` and `20261106170000_house_seed_2.sql`, both written by `supabase/seed/make_house_players.py`): accounts run by the developer that take a seat when nobody else is searching. The search bar fills over a random span (now and then at once, mostly 2–10 s; `seekSpan()`); a human seeking the same game within it is paired first (the seek stays in `seeks` until then); at its end the client asks `house`, and `gc_house_pair` seats a house player that is around at this hour (`online_from`/`online_hours`, UTC), free, close in rating (a different one than last time, a little chance in it), as a normal game with `games.house` (its colour) and `house_style` (its level and manner). **The human's device plays for it**: the engine picks the move at the house player's level, a think-time model says when (`housePace`: once per game it means to spend 55–95 % of the base time over some forty moves plus most of the increment, so its clock runs down like anyone's; `houseThinkMs`: quick in the opening and recaptures, longer with more to think about, a long think now and then, hurried in time trouble, scaled by `tempo` and a little by level), and the move goes to the server with `house: true` and the time it took (`think`), from which the server counts the house side's clock (`flagged()` never fires for the house side by the wall clock, so walking away during its turn wins nothing: the game waits for the human, however long; `gc_house_pair` doesn't count a live game that hasn't moved for an hour as keeping its house player busy). Its manner: resigns a lost game after a while (`resignAt`, `resignP`; weak ones never), takes a draw in a level long game (`draw`, `drawAt`), offers one in a dead one, sometimes flags in time trouble (`flag`), rarely doesn't show up for the first move (`abort`) or leaves mid-game (`leave`: seen to go away, and after the 20 s the game is lost on its device's word, `house_act leave`), mostly takes a rematch (`rematch`) and sometimes asks for one; `house_act` carries resign / draw / rematch. Rated like any game; the house player's rating moves by Glicko and then drifts a quarter of the way back to its `target` (`HOUSE_DRIFT`, `HOUSE_RD_MIN`). Its engine level is the one nearest `target` + ~300 (`20261106180000_house_levels.sql`): the ratings shown here run like chess.com's, some 300 below the engine's Elo scale (calibrated against Stockfish), so a "1500" house player plays at level 6 (1900). The first moves come from the opening book (`src/book.js`, 150 club lines in SAN, weighted; `GCBook.pick(moves, level)`, weaker levels leave it sooner and stray more), played quickly (`bookThinkMs`); out of the book the weak levels play the opening closer to their best move (half the eval noise, a tighter sampling, and `humanPrior` against pieces going home, king walks, rook shuffles and edge pawns before move 10). The same book and opening play apply to the bots. A tap on the opponent's bar opens their page (see Player pages); a house player's ends with "Account run by the developer". Tests: `test/server/logic.test.mjs` (memory and Postgres), the house section of `test/online_e2e.py` (`__gcSeekMs`, `__gcFastBot`, the mock server's `addhouse`).
- Leaving (`GONE_MS` = 20 s, table `seen`): while the game is in front of the player (tab visible, app in the foreground) the client tells the server so every `SEEN_MS` = 5 s (`seen`; one last time at the moment the app goes to the background, nothing while it is there) and keeps its Realtime presence tracked; in the background it untracks (the other side sees the "away" dot). Thinking for any length of time with the game in front changes nothing, and being away during the opponent's turn is fine for as long as it takes: the game waits. But the side to move whose device has been quiet for 20 s, once its turn is 20 s old, has left and loses (`reason: 'left'`, rated like a resignation; before move two the first-move rule aborts instead). The server decides it in `settle()` from `seen` rows — reached by the opponent's own heartbeat or `claim`, or by the leaver's late `seen` / `move` — and a device that never said it was there (an older client) is judged by its clock alone. The other screen shows the countdown "Opponent left · you win in N s" (`awayTick`, from presence and `turn_started_at`) and claims at its end. House players never leave by silence; their rare walk-away is `houseLeave` → `house_act leave`. Tests: the "left" sections of `test/server/logic.test.mjs` and `test/online_e2e.py` (`__gc.away(flag)`, the mock server's `/presence` and clock `shift`).
- Player pages (`openPlayer`, view `player`): anyone's ratings by pool, the score against you, and their recent games, each opening on the board with its review (back leads to the page: `game.fromPlayer`). Public reads (`SupaNet.player`: profiles + ratings; `history(uid)`; the mock server's `/player`). Reached from the opponent's bar in a game, from a row of the leaderboard (`lb-row`, `data-uid`) and from the score card on the games page. The leaderboard also shows the player's own place in the pool (`SupaNet.rank`, a count of those above; `A.top` answers `rank` through `repo.rankOf`).
- The result card (`showOver`, `.sheetdlg.over`, centred on every screen): the two players face to face (`faceoffHtml`: avatar, name, rating after the game with its change, each side's Joker Move), the score between them — today's series on this device (`noteSeries` / `seriesScore`, localStorage `series`, a sitting of up to three hours) beside the all-time score (`matchScore`), one bright action (Rematch, or Play again against a bot) with the review under it and a new opponent as a quiet line.
- Avatars (`20261106190000_avatars.sql`): a player's picture lives in the public storage bucket `avatars` as `<uid>.jpg` — chosen on the Profile tab (the picture is a button with a camera badge, `avatarSheet`), squared from its middle and shrunk to 256×256 JPEG on the device (`fileToAvatar`), uploaded by the client (`uploadAvatar`; storage policies let a player write only their own file) and then noted on the profile by the `avatar` action (`profiles.avatar_v`, a version that also busts the cache; 0 = none). `avatarHtml(uid, name)` shows the picture or the initial everywhere a name is: the game bars, the result card, the leaderboard, the player page, the start screen chip; the two sides' versions are read when a game opens (`profilesOf`). The mock server keeps pictures in memory (`/avatar`, `/avatar/<uid>`).
- The search dialog (`showLobbyDialog`, centred on every screen): the time control and the seconds, a line about who is around — "12 players online · 3 games on" from the `lobby` action (players seen by `hello` in the last five minutes (`profiles.last_seen`, `20261107100000_lobby.sql`), heartbeating in a game or seeking; games playing and touched within the hour; fresh seeks), polled every few seconds while the search runs — and a light line of what "we" are up to meanwhile (`lobbyMoods`, rotating).
- The leaderboard (`renderRatings`): the `top` action answers the top 50, the pool's size (`total`), the caller's place (`rank`) and, when they are outside the top, their own row (`me`), which the page pins below the list after a gap. My card shows my place and the share of players I am ahead of ("#42 of 230 · top 18%", the percentage only within the upper half); the first three wear podium marks. Lists that load (ratings, games, a player's page) show grey rows in their shape meanwhile (`skeletonRows`).
- Sheets and dialogs (`openDialog`): frosted glass, the way the phone's own sheets look — the page behind blurs under the veil, the sheet is translucent with a hairline edge; on phones it rises from the bottom edge to edge with a grabber (`sheet-handle`, drag it down to close; `sheetDrag`) and leaves the way it came; dialogs marked `.center` (the result card, the search) float in the middle on every screen. The game menu (`showMenu`) is an inset list with the icons in tinted tiles.
- Haptics (`haptic(kind)`, the Capacitor Haptics plugin in the app, `navigator.vibrate` on Android's web): a few moments only, never every move — the opponent found, a Joker Move by either side, a check against me, the end of a game, the 20-second warning (which also plays the soft `lowtime` sound once, when 20 s are left on my own turn). Settings → Vibration turns it off (`settings.haptics`).
- Sounds (`src/ui/sound.js`, synthesized): moves are crisp mechanical clicks in the family of the pick-up tick (`snap`: a bright snap with a lower click 4 ms behind it, no boomy body); a capture adds a second, lower click, castling clicks twice, a check adds the chime. The Joker Move is a gilded chime.
- Latency: the function talks to Postgres directly (postgres.js over `SUPABASE_DB_URL`, moved to the project's PgBouncer on port 6543 so a crowd of workers shares one small pool; the direct address if the pooler fails; `GC_DB_POOL=off` keeps it direct), runs in the database's region (`?forceFunctionRegion=eu-central-1`), and clients send CORS-simple requests (text/plain body with the token inside), so no preflight round trip. Every response carries a `Server-Timing` header (auth, db, total).

## Game review and history

- **Review** (as on chess.com): the engine searches every position to depth 10, at most 1.2 s (`Engine.reviewStep`; the same depth everywhere keeps the verdicts steady; when its best move is golden, a second search without Joker Moves says how much the Joker Move gains). Up to four workers share the game, each a stretch of it. `src/review.js` turns the scores into each side's accuracy (Lichess's formula over winning chances), the class of each move (brilliant, great, best, excellent, good, inaccuracy, mistake, miss, blunder, and *missed Joker Move*), a game rating (accuracy → Elo, calibrated on bot games, from 8 moves on) and a mark per phase. The **report** opens after the game (Game review): accuracy, the classes for both sides, game rating, rating change, phases, the Joker Move each side played, and, highlighted on top, the **missed Joker Moves** (tap one to see the moment). **Start review** steps through the moves with the coach: the class, a sentence on why, built from the engine's lines (`GCReview.story`): what the opponent's best answer does (takes a piece, a Joker Move, hits the queen), what the line wins or loses ("Black answers with the Joker Move Nb8★f4, attacking the queen. In the end Black wins the exchange and a pawn."), a Joker Move inside the line ("Key move: the golden Ra1★g1"). On a weak move the board shows that answer as an arrow. Buttons read as a sentence: **What follows** plays the line after the move on the board, **Best: Nf3** (the move's name on the button, gold) plays the best move and its line, both turn into **Back** (to the game; Esc too); **Find it yourself** puts the position before the move back and lets you find a move: the best one is recognised at once, any other is searched to the review's depth and graded (Try again, Best: …, Back). Phones show short labels (Next moves, ★ Nf3, Try it) and keep the coach one height, so the board doesn't jump.
- A review is kept on the device (`goldenchess.reviewCache`, last 40 games; accuracy per game in `goldenchess.reviewSums`), so a reviewed game opens at once and its row in the history shows the accuracy.
- **History**: Profile shows the latest games, All games lists them (online games from the `games` table, newest first, 50 at a time; games against the bots and on one device are kept on the device, newest 200). Chips above the list (and in Profile) give the score against each opponent over all games (`head_to_head()` in the database), in points as a match is counted (a draw is ½ each), and open that opponent's games with a score card (You 34 : 28 Boris, 32 wins, 4 draws, 26 losses). The result card of an online game shows the same score with the game just finished counted (asked for when the game opens, so it is there at once); a tap opens the games against that opponent. A row opens the game on the board with its report; back returns to the list, and a game in progress on the device is left as it was.
