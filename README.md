# Golden Chess

Chess plus one **golden move** per player per game: a queen, rook, bishop or knight teleports to any empty square. No capture, no check on the opponent's king afterwards, own king must be safe (so it can block a slider check). Kings and pawns can't use it. Everything else is standard chess; a rook that teleports loses its castling right.

Play: https://golden-chess.com (bot, two players on one device, online rated games, invite a friend by link).

The site has five tabs, like a chess site: **Play** (time control, Play, Play a friend by link or on one device), **Bots** (eight characters, one per engine level, from Pip at 600 to Golden at 2500), **Learn** (what the golden move is, autoplay boards, three one-move puzzles), **Ratings** (leaderboard per pool) and **Profile** (name, ratings, the latest games, settings). A bottom tab bar on phones, a side rail on wider screens; the address hash names the tab (`#play`, `#bots`, `#learn`, `#ratings`, `#profile`, `#games`, `#signin`, `#game`), so the browser's back button works. Each screen has one main action in gold and at most one quieter one. Online play needs an account (email code, free); bot and two-player games don't. Bot games have no clock, and the bot takes a human-like pause before each move (shorter in the opening, on forced moves and recaptures, longer in rich positions and before its golden move).

## Online play

- Clients only read the database; every change goes through the `play` edge function, which replays the game with the same rules module, checks the move, runs the clocks on server time (150 ms lag credit per move) and settles results and ratings.
- Writes are guarded by a row `version`, so two simultaneous requests can never both apply.
- Each state change is broadcast on a private Realtime channel `g:<game id>`; clients also poll as a fallback. Own moves are shown at once and confirmed by the server; a rejected move rolls back.
- A flag falls on the server: the client that sees a clock at zero asks the server to settle it (`claim`). A player who doesn't make a first move within 30 s gets the game aborted.
- Matchmaking pairs the closest rating with the same time control and rated/casual choice. Invites are links (`?join=<id>`); a third person opening one watches.
- Accounts: a visitor starts as a guest (Supabase anonymous sign-in). Online play (Start Game, Play a Friend, opening an invite link) asks a guest to sign in first; the chosen action is remembered (`goldenchess.pending`, 30 min, also across a reload or the email link) and continues right after. Signing in adds an email to that same account (`updateUser({ email })` + a 6-digit code, `verifyOtp` type `email_change`), so anything the guest had stays, an email that already has an account signs in to it (`signInWithOtp` + code, type `email`). After any sign-in a player without a name of their own is asked for one (`profiles.name_chosen`, set by a trigger when the `rename` action saves a name; the name on the Google account is offered); Profile → Change name opens the same form. The email also carries a one-tap link for the same device. The server marks a profile registered (`profiles.is_guest = false`) from the token's `is_anonymous` claim. Sign out leaves a fresh guest. Email templates and the Auth settings they need: `supabase/emails/README.md`. Google never talks to Supabase's address, so its pages name golden-chess.com: on the website Google's own button (Google Identity Services, client `googleClientId` in `build.js`); in the app (Google refuses sign-in inside a web view) and on the website without Google's script, Google's sign-in page (`response_type=id_token`) answers to `google.html`, which hands the ID token back (the app: through the system browser and `goldenchess://auth`; state and nonce are checked against `goldenchess.gFlow`). The ID token is linked to the guest (`linkIdentity({ token, nonce })`) or, when that Google account or its email already has a player, signs in to that player (`signInWithIdToken`, then the page starts over as them). The Google client needs only golden-chess.com: JavaScript origin `https://golden-chess.com`, redirect URI `https://golden-chess.com/google.html`. The iPhone app offers only the email code (`googleShown()`): the App Store asks for Sign in with Apple next to any other company's sign-in (guideline 4.8), and the same email reaches the same account.
- Latency: the function talks to Postgres directly (postgres.js over `SUPABASE_DB_URL`, REST API as a fallback), runs in the database's region (`?forceFunctionRegion=eu-central-1`), and clients send CORS-simple requests (text/plain body with the token inside), so no preflight round trip. Every response carries a `Server-Timing` header (auth, db, total).

## Game review and history

- **Review** (as on chess.com): the engine searches every position to depth 10, at most 1.2 s (`Engine.reviewStep`; the same depth everywhere keeps the verdicts steady; when its best move is golden, a second search without golden moves says how much the golden move gains). Up to four workers share the game, each a stretch of it. `src/review.js` turns the scores into each side's accuracy (Lichess's formula over winning chances), the class of each move (brilliant, great, best, excellent, good, inaccuracy, mistake, miss, blunder, and *missed golden move*), a game rating (accuracy → Elo, calibrated on bot games, from 8 moves on) and a mark per phase. The **report** opens after the game (Game review): accuracy, the classes for both sides, game rating, rating change, phases, the golden move each side played, and, highlighted on top, the **missed golden moves** (tap one to see the moment). **Start review** steps through the moves with the coach: the class, a sentence on why, built from the engine's lines (`GCReview.story`): what the opponent's best answer does (takes a piece, a golden move, hits the queen), what the line wins or loses ("Black answers with the golden move Nb8★f4, attacking the queen. In the end Black wins the exchange and a pawn."), a golden move inside the line ("Key move: the golden Ra1★g1"). On a weak move the board shows that answer as an arrow. Buttons: **Show follow-up** plays the line after the move on the board, **Best** plays the best move and its line, both turn into **Hide** (back to the game; Esc too); **Retry** puts the position before the move back and lets you find a move: the best one is recognised at once, any other is searched to the review's depth and graded (Try again, Best, Hide). Phones show short labels (Show, Best, Retry) and keep the coach one height, so the board doesn't jump.
- A review is kept on the device (`goldenchess.reviewCache`, last 40 games; accuracy per game in `goldenchess.reviewSums`), so a reviewed game opens at once and its row in the history shows the accuracy.
- **History**: Profile shows the latest games, All games lists them (online games from the `games` table, newest first, 50 at a time; games against the bots and on one device are kept on the device, newest 200). Chips above the list (and in Profile) give the score against each opponent over all games (`head_to_head()` in the database), in points as a match is counted (a draw is ½ each), and open that opponent's games with a score card (You 34 : 28 Boris, 32 wins, 4 draws, 26 losses). The result card of an online game shows the same score with the game just finished counted (asked for when the game opens, so it is there at once); a tap opens the games against that opponent. A row opens the game on the board with its report; back returns to the list, and a game in progress on the device is left as it was.

- `node test/golden.js` — golden-move rules + random-play fuzz
- `node test/engine.js` — tactics incl. golden block, mate finding, KQK conversion
- `node test/server/logic.test.mjs` — server: pairing, invites, legality, clocks, flags, aborts, draws, rematch, ratings, concurrent writes; `PG=1` runs the same tests on real Postgres (PGlite) through postgres.js with the production migration (dev deps in `test/server/package.json`)
- `DENO=<path to deno> node test/server/edge-local.mjs` — the production `index.ts` under Deno against PGlite, with a fake JWKS (ES256 tokens) and a fake Realtime endpoint
- `python3 test/online_e2e.py` — two browsers play each other through `test/server/mock-server.mjs` (same server logic, in-memory store, SSE instead of Realtime): pairing, moves, premoves, golden move, clock sync, draw offer, reload, dropped realtime, flag, rating change, rematch, abort, invite link, spectator
- `python3 test/account_e2e.py` — accounts through the mock server's stand-in for Supabase Auth (codes land in an outbox): Start Game sends a guest to the sign-in page and the search starts after it, a new account keeps the guest's id and picks a name (a taken one is refused), signing in from Profile and Ratings returns there, a second device signs in and is the same player, sign out, wrong code, resend limit, refused during a live game, expired link
- `python3 test/bot_think.py` — the Bots tab, no clock in bot games, the bot's thinking pause (never instant, varies, quick forced moves, longer before a golden move)
- `node test/learn.js` — the Learn tab: scripted moves are legal, the "mate in normal chess" positions are mate, every accepted puzzle answer wins or saves the game and every other golden move scores clearly worse (engine)
- `python3 test/targeted.py`, `python3 test/review_test.py`, `python3 test/stress.py <seed> <games>` — offline UI flows, review, randomized input with a per-frame consistency monitor
- `node test/review_report.js` — the review's classes and missed golden moves on real games (`test/fixtures/games.json`), and the coach's reason on `test/fixtures/coach.json` (8.Qe2 allows the golden Nb8★f4; 8.hxg4 Qxh1+ Ra1★g1 was best)
- `python3 test/coach_e2e.py` — the coach on that game, phone and computer: the reason, the punishing answer as an arrow, Show follow-up / Best / Hide / Esc, Retry (the best move recognised, a weak one checked, Try again), Russian

- `python3 test/native_app.py` — the site inside the iPhone / Android app, with stand-ins for the app's bridge and for supabase-js: Google opens in the system browser and comes back through `goldenchess://auth` (same player, another player, a link taken once, a link the app was started with), the name asked after a sign-in, Google's button on the website (ID token, nonce, an email that already has a player), Google's page through `google.html` for the app and for the website without Google's script (state, nonce, cancel, a foreign answer), the Android back button, the system share sheet for invites, the app's offline copy, no Google on the iPhone

## The app (iPhone / Android)

`app/` is a Capacitor 8 shell around the live site, with the site's offline copy (`app/www/index.html`, made by `build.js`) for launches without internet. Every change under `app/` builds an Android test APK (release `android-test`) and checks the iPhone project in `.github/workflows/app.yml`. Steps for Xcode, Android Studio and the stores: `app/README.md` (in Russian).

## Deploy

`node build.js`, copy `dist/web/index.html` and `dist/web/og.png` to the repository root, push to `main`. GitHub Pages serves the site; the Supabase GitHub integration applies new migrations and deploys the `play` function.
